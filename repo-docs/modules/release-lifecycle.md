# 发行版获取与兼容性

准备升级时，读者需要先回答两个问题：上游发布了什么，这些文件是否适合当前引擎。下载入口负责前一个问题；固定输入构建、登记审查和设备验收负责后一个问题。任一阶段通过都不会自动替下一阶段作结论。

## 从官方发行获取候选输入

查询直接读取官方发行元数据。`stable` 选择正式发行；`prerelease` 包含预发行，按发布记录选择最新项，并不是只按版本字符串排序。默认正式通道没有可用发行时会报错，不悄悄切换通道。

```sh
mumu-resukisu fetch-release --check
mumu-resukisu fetch-release --channel prerelease --check
mumu-resukisu fetch-release --channel prerelease --output inputs/release-review
```

输出目录必须是新目录，查询模式不会下载文件。下载包含管理器 APK、解析到具体提交的源码归档和可追溯清单；保留元数据来源、摘要、长度、标签与提交。归档不自动解包，APK 不执行，也不触发写盘。

目录中的 `release.json` 记录本次选择，APK 保留官方文件名，源码归档名为 `source-<完整提交>.tar.gz`。APK 必须具备上游提供的 SHA-256，下载后比对长度与摘要；源码归档的摘要由本地计算，`upstreamDigestVerified` 为 false。传输完成后再次核对标签及制品记录，中途替换会使本次操作失败，临时下载不会作为完成目录交付。

上游原 ReSukiSU 仓库已更名为 [Baka-SU/BakaSU](https://github.com/Baka-SU/BakaSU)。获取器按固定仓库身份核对官方来源，同时保留查询时的实际名称；这个名称变化不自动改变本项目历史适配补丁、管理器包身份或支持清单。若官方身份或制品形状发生未知变化，应明确失败并由维护者审查。

“最新”指运行查询时获取的发行记录。API 限流、网络失败、无法完整遍历发行列表或缺少所需摘要时，工具报错，不用旧缓存冒充当前最新版。

## 下载成功后还差什么

| 阶段 | 得到的证据 | 仍不能声称 |
| --- | --- | --- |
| 查询与下载 | 官方发行记录、制品摘要、标签对应的源码提交 | APK 一定由该源码可复现构建，或可在目标引擎运行。 |
| 离线登记 | 完整 APK 签名、固定签名者、包身份、唯一 x64 daemon 与 UAPI | 已经允许在启动时使用该版本。 |
| 代码审查与构建 | 支持清单、配套加载器和探针已同步，模型通过 | 模拟器冷启动与升级路径已通过。 |
| 目标设备验收 | 本次候选在明确目标的实际行为 | Android 12、其他内核、任意模块也兼容。 |

例如，新版 APK 的下载摘要正确，但包名或 UAPI 已变化：下载阶段可以成功，现有登记器仍会拒绝。正确处理是审查变化及适配工作，不能为了完成登记直接放宽期望值。

源码标签解析只确认一个发行记录对应的 Git 标签目前指向哪个提交。固定原生构建采用的是经过适配的明确提交，可能与发行标签不同；维护者仍需核对 APK 和源码的对应关系，不能把标签查询当成可复现构建证明。

归档用于保存可追溯输入，不含 Git 元数据。现有构建器与登记器要求 Git 工作树和实际提交；必须另行准备该提交的 Git 检出，不能把下载归档目录直接传入 `--source-root` 或 `--resukisu-source`。

## 支持清单如何改变

离线登记器只在新的构建目录输出 `entry.json` 与 `proof.json`，明确记录 `catalogUpdated: false` 和 `deviceUpgradeValidated: false`。登记要求维护者显式确认源码与 APK 的关联，随后通过代码审查更新清单、探针版本及编译输入；启动预置遇到未知 daemon 时保留原件并阻止继续启动。

实际命令和所需工具见[构建与版本登记](../../docs/build-and-use.md)。实现入口位于[发行获取器](../../src/mumu_resukisu/releases.py)、[离线登记器](../../scripts/register-release.py)和[启动支持清单](../../native/prestage/supported-daemons.json)，验证入口为[下载边界测试](../../tests/test_releases.py)与[登记边界测试](../../tests/test_release_registration.py)。
